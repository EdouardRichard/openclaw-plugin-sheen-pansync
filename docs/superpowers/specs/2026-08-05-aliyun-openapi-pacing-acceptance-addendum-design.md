# 阿里云盘 OpenAPI 节拍补充设计

**日期：** 2026-08-05

**状态：** 用户已批准方案，待书面复核

## 背景

本地自动化门禁全部通过后，真实 OpenClaw 账号验收仍稳定复现五文件下载的第四、第五个 `DOWNLOAD_FAILED`：第一批三个文件全部成功，第二批两个文件均在约 0.6 秒内失败，且未形成本地文件。

下载并非只调用一次取下载地址接口。每个 `pan_sync_download` 在进入内容流阶段前还会获取资源盘上下文和文件元数据；两个下载并行时会在短时间内启动至少四个 OpenAPI 请求。现有组合 15 QPS 滑动窗口允许这类突发，不能满足实机表现出的约 3 QPS 约束。

## 获批方案

在共享的 `AliyunOpenApiRateLimiter` 中增加进程内全局 FIFO 启动节拍：任意两个阿里云 OpenAPI 请求的实际 HTTP 启动时间至少间隔 350 ms。第一项请求可立即启动，后续请求按入队顺序等待。

现有端点专属滑动窗口继续保留：

- `openFile/list`：40 次/10 秒；
- `openFile/getDownloadUrl`：10 次/10 秒；
- 其他 OpenAPI：保留既有规则；
- 全局 350 ms 最小启动间隔作为更保守的组合保护，不宣称为官方公布配额。

上传分片使用的是签名 PUT 地址，不进入 OpenAPI 节拍器；其既有顺序上传和相邻 PUT 至少 350 ms 的规则保持不变。

## 取消与错误处理

- 等待节拍期间使用调用方的 `AbortSignal`；取消的请求从 FIFO 队列移除，不发送 HTTP 请求，也不占用后续启动时间。
- 不新增自动重试，不把普通 `403` 推断为限流。
- 继续使用现有稳定错误码，不向 Tool、日志或验收记录暴露 Token、签名 URL、网盘 ID、文件名或绝对路径。

## 测试与验收

实现遵循 TDD：

1. 先增加失败测试，证明前三个混合端点请求不再同一时刻突发，而是分别在 0、350、700 ms 获准；第四个在 1,050 ms 获准。
2. 覆盖等待中的取消不会阻塞下一请求。
3. 运行限流器聚焦测试与完整 `npm run verify`。
4. 构建当前提交的精确 tarball，重新安装到本地 OpenClaw，验证插件、三项 Tool 与 Gateway 健康。
5. 真实账号只再执行一次五文件下载，沿用已列出的文件选择，不重新列目录、不重试、不做 429 压测。

成功标准是五次下载均返回 `downloaded`，且省略 `localDirectory` 时五个文件均落在 OpenClaw 工作区根目录。若仍失败，立即停止真实请求并报告实际边界，不继续试探限流阈值。

## 非目标

- 不改变三槽下载内容流并发门禁和 Skill 的 3+2 批次规则。
- 不增加跨 Gateway 进程的分布式限流。
- 不改变分片大小、上传协议、Token 获取方式或资源盘唯一路由。
- 不删除远端文件，不提交远端代码，不推送或创建 PR。
